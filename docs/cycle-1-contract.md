## Две базы, не одна куча

Сырой интернет и оценки **не** кладём в CRM. В CRM только те, кому уже можно писать.

| База | Где | Что лежит | Чего нет |

| **Склад анализа** | Postgres цикла 1 (`evorove_lead`) | Бриф клиента, следы из открытого веба, извлечённые кандидаты, оценки, отказы с причиной | Письма, вкладки продажи, слоты |

## Как собираем данные

Три захода. Следующий не начинается, если предыдущий пустой.

### 1. Бриф — не лиды

**Откуда:** публичный сайт клиента (указала URL), по желанию её файлы, по желанию её открытые объявления (Microsoft Ad Library — только бриф, показы EEA, не люди США).

**Что достаём:** услуга; кому может подойти; география (США, город/зона, если есть); чего нельзя обещать (цены/скидки/гарантии/юрclaim, которых нет у неё на странице).

Сайт клиента **запрещён** как источник людей: ни формы, ни «нам написали», ни комментарии «я ваш клиент».

Бриф не готов — в интернет за людьми не идём.

### 2. Следы в свободном поле — ещё не лиды

**Откуда:** открытый веб по запросам из брифа (услуга + аудитория + место). Публичные страницы, посты, объявления о потребности, локальные следы. Не LinkedIn-скрейп, не пейвол, не внутренности Google Ads Transparency, не купленная база телефонов.

**Что кладём в склад анализа (след):** URL, дата съёма, текст/видимое, какой запрос из брифа привёл, язык, намёк на гео.

След про клиента (его же сайт, его же отзыв «я хожу сюда») — не след для генерации.

### 3. Люди из следов — ещё не Cold

Из следа, который прошёл анализ, извлекаем: имя если есть, email и/или телефон, факт о **его** ситуации, URL источника, канал `email` или `sms`.

Нет факта или нет контакта — в складе как отказ, не в CRM.

## Как анализируем и по каким метрикам

Не «есть ли слова H1 сайта в строке». Качество — ответ на вопрос: **этому человеку услуга этого клиента в США реально может подойти, и цикл 2 сможет ему написать.**

### Анализ брифа

| Метрика | Проход |
| --- | --- |
| Есть услуга | Понятно, что продаём, из её слов, без выдумки |
| Есть аудитория | Понятно, кому это живое дело |
| Есть рынок | США; локальность, если дело локальное |
| Коммерция | Не обещаем то, чего нет у неё на странице |

Любая дыра → статус «бриф не готов», поиск людей стоп.

### Анализ следа (сырые данные)

| Метрика | Проход |
| --- | --- |
| Не свой сайт | Документ не принадлежит клиенту |
| Тема | След про потребность / аудиторию / ситуацию, не про что попало |
| Гео | США или зона услуги, если зона в брифе |
| Открытость | Публичный http(s), не логин, не пейвол |
| Свежесть | След ещё имеет смысл (не архив десятилетней давности без живого сигнала) |

След не прошёл → храним отказ в складе анализа, людей из него не собираем.

### Повторный анализ человека (качество лида)

Все пункты обязательны. Нет одного — не Cold.

| Критерий | Качественный лид | Брак |
| --- | --- | --- |
| **Адрес** | Валидные email или телефон, канал ясен | Голое имя, ник, «есть в интернете» |
| **Факт** | Конкретная ситуация человека (ищет услугу, описывает задачу, публично просит помощи в этой теме) | «Есть телефон», повтор слогана клиента, пустая строка |
| **Источник** | Откуда факт: URL или явная фиксация съёма | «базы», «LinkedIn dump» |
| **Совпадение с услугой** | Факт бьётся с тем, что клиент продаёт | Соседняя ниша, конкурент, который сам продаёт то же |
| **Совпадение с аудиторией** | Человек из круга «кому это может подойти» | Случайный контакт в том же городе |
| **Гео** | США и зона, если зона есть | Другая страна при локальном деле |
| **Не свой** | Не действующий клиент этого бизнеса по следу | «Хожу к вам каждую неделю» |
| **Не свалка** | Одна живая причина, не список номеров | Купленный файл, дописанный оффер к телефону |

Оценка в складе анализа (для отладки, не для владельца как дашборд):

- **fit** — насколько факт и бриф про одно дело (0–1);
- **evidence** — насколько факт конкретный и привязан к источнику (0–1);
- **addressable** — 1, если контакт пригоден для цикла 2.

На Cold идут только те, у кого все три выше порога **и** все критерии таблицы «да». Порог не «процент закрытия клиенту». Это внутренний отбор, чтобы на доске не было мусора.

Владельцу на Cold видна **причина человеческим языком**, не баллы. Баллы остаются в складе анализа.

## Кому писать на холодную

Пишет **цикл 2**, не цикл 1. Цикл 1 решает только: **можно ли положить на Cold**.

Класть в CRM Cold, если:

1. Бриф готов.
2. Человек извлечён из открытого следа, не с сайта клиента.
3. Повторный анализ пройден (таблица выше).
4. Есть причина + источник + канал.
5. Его ещё нет на доске этого тенанта с тем же контактом.

Не класть, если нет согласия на отправку: согласие проверяет цикл 2 в момент письма (TCPA / opt-in / STOP). Качественный лид ≠ «уже можно слать SMS». Качественный лид = «есть зачем писать и чем адресовать». Без разрешённого согласия цикл 2 не отправляет, карточка может остаться в Cold.

## Код сейчас (честно)

Сайт клиента читается как текст. Отбор в коде всё ещё цепляется к цитатам страницы — это **старая неверная метрика**, её менять под этот контракт. Поиск по умолчанию не подключён. Cold в CRM из генерации не наполняется.

Склад анализа (Postgres цикла 1) физически есть: таблицы `briefs`, `hypotheses`, `traces`, `rejected_traces`, `candidates`, `hypothesis_outcomes`, тенант-скоуп по `business_id` (миграции в `migrations/`, порт 5435, отдельная база от `evorove`/`evorove-crm`). `LeadGenerationEngine` пишет туда сырой след и решение по каждому кандидату при наличии `business_id` — без похода в CRM.

`hypothesis.py` тоже есть: `build_hypotheses(offer, geo_radius)` строит гипотезы по каждой аудитории из брифа (`demographic_fit`) плюс `public_ask`/`need_statement` вокруг основной услуги; `verify_hypothesis` прогоняет гипотезу через лёгкий `HypothesisProbe` и метит её `dead`, если ни один след не прошёл базовую планку кандидата (адрес + факт + источник); `prioritize_hypotheses` сортирует живые по измеренным `fit_score`/`evidence_score`, без выдуманных весов (используется будущим `reweight_hypotheses.py` из фазы 4, не движком напрямую).

Первый живой `PeopleSearch`-коннектор подключён: `WebSearchPeopleSearch` (`web_people_search.py`) + `HttpSearxngWebSearchClient` (`web_search.py`). Источник URL — не платный поисковый API, а self-hosted метапоисковик (SearxNG-совместимый JSON-эндпоинт, `WEB_SEARCH_BASE_URL` в `.env`); дальше свой код: тематический фильтр по ключевым словам гипотезы → проверка публичности URL → свой fetch страницы → извлечение email по regex (телефон из тела страницы намеренно не извлекается — слишком шумно). `LeadGenerationEngine._generate_via_hypotheses` прогоняет каждую гипотезу от `build_hypotheses`, пишет каждый сырой след в `traces`, след без кандидата — в `rejected_traces`, кандидата — в `candidates` (cold/rejected), дедуплицирует один и тот же контакт между гипотезами за один прогон (иначе один человек уходил бы в CRM несколько раз). Существующая логика `candidate.py` (`accept_candidate_for_offer`) не менялась. `geo_radius` — явный параметр движка (`GeoRadius`, по умолчанию весь рынок США); автоматический вывод города/зоны клиента из брифа ещё не сделан.

Ограничение источника: реальный охват зависит от того, что вернёт конкретный SearxNG-инстанс (какие движки он агрегирует) — это конфигурация владельца, не код.

`hypothesis_id` теперь доезжает до Cold: `Cycle1Handoff.hypothesis_id` и payload в `crm_touch.assembled_touch` несут его как метаданные (не PII) — предпосылка для фазы 3.

Появился первый сетевой код репозитория: `api.py` (`uvicorn evorove_lead.api:app`) — единственный вход, `POST /api/v1/internal/hypothesis-outcomes`, за тем же `INTERNAL_TASK_SECRET`, что и исходящий CRM-тач (константное сравнение, как в `evorove-crm`). Принимает только `business_id, hypothesis_id, case_id, outcome` — в схеме физически нет поля для имени/контакта/текста. Пишет в `hypothesis_outcomes` через тот же `AnalysisWarehouse`. Сторону, которая шлёт сюда события — `evorove-crm`'s `record_case_state` при переходе `ProcessState` в `BOOKED`/`PAID` (Done) или `LOST`/`CANCELLED` (явный отвал) — уже сделала (не в этом репозитории).

Фаза 4 тоже сделана: [`reweight_hypotheses.py`](../src/evorove_lead/reweight_hypotheses.py) — джоб, не часть движка — считает `accept_rate` (доля кандидатов, дошедших до Cold) и `close_rate` (доля из Cold, дошедших до `done` в `hypothesis_outcomes`) по каждой гипотезе одного бизнеса; при накопленной выборке (`MIN_SAMPLE_FOR_RATING`, сейчас 3) низкий `close_rate` → `paused` и бюджет (`query_budget`) в ноль, высокий → `+1` к бюджету (потолок `MAX_QUERY_BUDGET`). Мёртвые (`dead`, из `verify_hypothesis`) джоб не воскрешает. `hypotheses` получил три новых поля: `accept_rate`, `close_rate`, `query_budget` (миграция `0002`).

Библиотека паттернов — [`pattern_library.py`](../src/evorove_lead/pattern_library.py) + `sqlalchemy_pattern_library.py`, таблица `hypothesis_pattern_library` (миграция `0003`) — **системная, без `business_id`**. Хранит `business_archetype → channel_family → query_pattern → observed_close_rate_band`, где `query_pattern` — это `intent_trigger.kind` (одно из четырёх известных значений), никогда не буквальный текст `query_template` (тот цитирует формулировки конкретного бизнеса). `reweight_hypotheses` пополняет её опционально (нужен явный `--archetype` в CLI); `build_hypotheses` может её читать (`pattern_library=`, `business_archetype=`) и переставляет местами уже построенные гипотезы по известному банду для архетипа — это только порядок, `fit_score`/`evidence_score` остаются честными нулями до `verify_hypothesis`. Архетип бизнеса нигде не выводится автоматически — вызывающий код должен передать его явно (в движке пока не подключено).
